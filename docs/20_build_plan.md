# План сборки MVP

> **Это план, а не отчёт.** На момент написания кода нет: ни одного `.py`-файла в проекте не создано, зависимости не установлены, Telegram API не подключался, токен не запрашивался и не создавался.
> Что именно строим — в `18_mvp_spec.md`. Как выглядит разговор — в `17_bot_conversation_flow.md`. Задания — в `19_mvp_questions.md`.

---

## Общие правила для всех этапов

1. **Этап — это 15–25 минут работы.** Если этап растянулся на час, значит, он был неправильно поставлен: надо остановиться и разрезать его пополам, а не героически доделывать.
2. **В конце каждого этапа — коммит.** Даже если сделано мало. Пять этапов — пять коммитов, это уже больше требуемого минимума в три осмысленных коммита.
3. **Токен не попадает в код и не попадает в Git никогда.** Он читается из переменной окружения. В репозитории лежит только `.env.example` с пустым значением. Файл `.env` закрыт через `.gitignore`.
4. **Проверки в конце этапа делаются руками и записываются.** «Вроде работает» — не проверка.
5. **Не забегать вперёд.** Соблазн на этапе 2 сразу написать всю логику заданий очень большой. Если поддаться, отлаживать придётся всё сразу.

---

## Что понадобится до этапа 1

Это подготовка, а не этап:

- установленный Python (версия 3.10 или новее);
- аккаунт в Telegram;
- токен бота, полученный у @BotFather, — **записать в локальный файл `.env`, который не попадает в Git**;
- библиотека для работы с Telegram. Достаточно любой одной; в плане ниже подразумевается `python-telegram-bot` — у неё простая работа с кнопками, а кнопки нам нужны на каждом шаге. Заменить на другую (например, `aiogram`) можно, план от этого не меняется.

**Ничего из этого пока не сделано.**

# Этап 1. Минимальная структура проекта и зависимости

**Время:** 15–20 минут.

### Какие файлы создать

```
school_oge_bot/
├── .gitignore            — уже есть
├── .env.example          — образец, БЕЗ настоящего токена
├── requirements.txt      — список библиотек
├── README.md             — уже есть, дописать раздел «Как запустить»
├── docs/                 — уже есть
└── bot/
    ├── __init__.py       — пустой
    ├── config.py         — чтение токена из переменной окружения
    ├── questions.py      — 5 заданий из 19_mvp_questions.md
    └── main.py           — точка входа, пока только запуск и остановка
```

Отдельно, **не в Git**: файл `.env` с настоящим токеном, создаётся локально руками.

### Что должно заработать

Бот запускается командой из терминала, подключается к Telegram, ничего не отвечает и корректно останавливается по Ctrl+C. На этом этапе это уже результат: если запуск работает, дальше вся возня будет только с логикой, а не с окружением.

`questions.py` содержит все пять заданий: текст, правильный ответ, объяснение при верном ответе, объяснение при неверном, название проверяемого признака. Никакой логики в этом файле нет — только данные.

### Три проверки готовности

1. `python -m bot.main` запускается без ошибок и не падает в первую секунду; Ctrl+C останавливает его без «портянки» из ошибок.
2. Если убрать токен из окружения, бот **не запускается** и пишет понятную строку вида «не найден TELEGRAM_BOT_TOKEN» — а не падает с непонятной ошибкой библиотеки.
3. `git status` **не показывает** файл `.env`, и `git ls-files` его не содержит.

### Коммит

```
Добавлена структура Python-проекта и 5 заданий MVP
```

# Этап 2. `/start` и выбор темы

**Время:** 20–25 минут.

### Какие файлы создать или изменить

- `bot/main.py` — добавить обработчик команды `/start`;
- `bot/texts.py` — **новый файл**: все тексты сообщений в одном месте, чтобы править формулировки, не трогая логику;
- `bot/keyboards.py` — **новый файл**: кнопки (тема, «Начать», ответы Н / НН / Не знаю, «Дальше»).

Тексты берутся из `17_bot_conversation_flow.md`, шаги 1–2.

### Что должно заработать

`/start` → приветствие с одной кнопкой темы «Н/НН в прилагательных и причастиях» → нажатие → сообщение про формат (5 заданий, ~5 минут, объяснение после каждого) и кнопка «Начать». Нажатие «Начать» пока ничего не делает или отвечает заглушкой «здесь будет задание 1».

Заданий на этом этапе ещё нет — и это нормально.

### Три проверки готовности

1. В настоящем Telegram `/start` доводит до кнопки «Начать» **максимум за 2 нажатия** — проверить на своём телефоне.
2. Повторный `/start`, отправленный посреди диалога, не ломает бота, а начинает всё заново.
3. Если написать боту произвольный текст, он не падает; в консоли нет ошибок.

### Коммит

```
Добавлены /start, экран темы и клавиатуры
```

# Этап 3. Пять вопросов и обработка ответов

**Время:** 25 минут. Самый большой этап; если не укладывается — разрезать на «показать задание» и «обработать ответ» и сделать два коммита.

### Какие файлы создать или изменить

- `bot/session.py` — **новый файл**: состояние одной тренировки (какое задание сейчас, сколько верных, где нажали «Не знаю», где нажали «Не согласен»). Хранение — самое простое, в памяти процесса;
- `bot/main.py` — обработка нажатий на `Н`, `НН`, `Не знаю`, `Дальше`, `Не согласен`;
- `bot/texts.py` — дополнить.

### Что должно заработать

Нажатие «Начать» показывает задание 1 с пометкой «1 из 5» и тремя кнопками. После ответа бот сразу пишет, верно или нет, показывает правильный ответ и объяснение из `19_mvp_questions.md`, затем кнопку «Дальше». И так все пять заданий подряд, в фиксированном порядке.

Рядом с «Дальше» появляется кнопка «Не согласен» — она ничего не меняет в счёте, только помечает задание.

### Три проверки готовности

1. Пройти все пять заданий, отвечая **только верно**, — все пять объяснений соответствуют своим заданиям, номера «N из 5» идут подряд и не сбиваются.
2. Пройти все пять заданий, отвечая **только неверно**, — то же самое: тексты правильные, ничего не перепутано. Затем пройти пятый раз, нажимая «Не знаю», — объяснение показывается, задание не засчитывается как верное.
3. Прокрутить чат вверх и нажать кнопку **старого** задания: счёт текущей тренировки не портится и бот не падает.

### Коммит

```
Показ 5 заданий, проверка ответа и объяснение после каждого
```

# Этап 4. Итог и `/stop`

**Время:** 20 минут.

### Какие файлы создать или изменить

- `bot/main.py` — экран итога, обработчик `/stop`, ответ на произвольный текст;
- `bot/texts.py` — тексты итога, разбора и прощания;
- `bot/session.py` — выбор совета по самому частому признаку ошибки (таблица в `17_bot_conversation_flow.md`, шаг 9).

### Что должно заработать

После пятого задания бот показывает «X из 5», отдельным сообщением — **одну** строку разбора по самому частому признаку ошибки, затем кнопки «Пройти ещё раз» и «Закончить».

`/stop` работает на любом шаге: одно прощальное сообщение, тренировка не досчитывается, после этого бот молчит до следующего `/start`.

На произвольный текст бот отвечает одной фразой, что понимает только кнопки.

### Три проверки готовности

1. Три прохода с разными результатами — 0 из 5, 5 из 5 и что-то посередине: во всех трёх случаях число верное, и совет соответствует тому, где реально были ошибки.
2. `/stop` нажат в трёх разных местах — на первом задании, после объяснения, на экране итога. Каждый раз бот прощается и **больше не присылает ни одного сообщения**.
3. Задания с «Не знаю» не попадают в число верных и отмечены в итоге отдельной строкой.

### Коммит

```
Добавлены итог тренировки, разбор ошибок и команда /stop
```

# Этап 5. Ручное тестирование и исправление

**Время:** 25 минут. Кода здесь пишется мало, а находится — много.

### Какие файлы создать или изменить

- `docs/22_manual_test_log.md` — **новый файл**: журнал ручного тестирования. Что делал, что ожидал, что получилось, исправлено или нет;
- любые файлы бота — по итогам найденных проблем;
- `README.md` — заменить честную пометку «бот ещё не собран» на реальную инструкцию запуска, **только после того как бот действительно запускается**.

### Что должно заработать

Полный проход бота по чек-листу «границы первой демонстрации» из `18_mvp_spec.md`, включая проход **с телефона**, а не только с компьютера.

### Что обязательно проверить руками

- полный проход от `/start` до итога — с телефона, с секундомером;
- `/stop` в трёх разных местах;
- произвольный текст вместо кнопки;
- двойное нажатие одной и той же кнопки подряд;
- нажатие кнопки старого задания после прокрутки вверх;
- перезапуск бота посреди тренировки: он не должен падать, когда пользователь нажмёт кнопку;
- два человека в боте одновременно — счёт одного не должен попадать другому.

### Три проверки готовности

1. Один живой человек, **не автор проекта**, проходит все пять заданий сам, без подсказок; замечания записаны в `22_manual_test_log.md` дословно.
2. Проход занял не больше 10 минут по секундомеру — время записано.
3. Ни одна из проверок выше не роняет бота с ошибкой в консоли; всё найденное либо исправлено, либо записано в журнал как известная проблема с пометкой «не исправлено».

### Коммит

```
Ручное тестирование MVP, журнал проверок и исправления
```

# Чего в этом плане намеренно нет

- базы данных — состояние тренировки живёт в памяти процесса, при перезапуске теряется, и это приемлемо для нескольких человек;
- вечерних напоминаний — на этапе проверки они отправляются вручную (`18_mvp_spec.md`);
- памяти о прошлом результате — если после этапа 5 останется время, это первое, что стоит добавить, но в пять этапов оно не входит;
- деплоя на сервер — бот запускается с ноутбука на время демонстрации;
- тестов на `pytest` — при пяти заданиях ручная проверка честнее и быстрее;
- админки, платежей, веб-панели, ИИ-генерации заданий.

# Что может пойти не так

| Что | Как заметить | Что делать |
|---|---|---|
| Токен случайно попал в код | `git status` или поиск по репозиторию находит длинную строку с двоеточием | Немедленно отозвать токен у @BotFather и выпустить новый. Старый считать скомпрометированным |
| Этап 3 не укладывается в 25 минут | Прошло полчаса, а задание 1 всё ещё не показывается | Разрезать на два: сначала «показать задание», потом «обработать ответ». Сделать два коммита |
| Бот отвечает не тем объяснением | Заметно только при ручной проверке всех пяти заданий | Проверять все пять и оба варианта ответа, а не одно наугад. Это прямо записано в проверках этапа 3 |
| Кнопки старых сообщений ломают счёт | Прокрутил вверх, нажал — счёт съехал | Проверка №3 на этапе 3 существует именно для этого |
| Два человека мешают друг другу | Счёт одного попадает другому | Проверка на этапе 5. Состояние должно храниться отдельно для каждого пользователя |
| Хочется добавить «ещё одну маленькую фичу» | Появляются файлы, которых нет в плане | Записать идею в конец этого файла и не делать. Границы MVP — в `18_mvp_spec.md` |
